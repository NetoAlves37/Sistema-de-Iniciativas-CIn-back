**O que foi olhado e não considerado problema:**

- `DivulgacaoFacade` só delega para `googleAgendaUrl` (parece um Middle Man), mas é a API pública do módulo, o que é intencional e correto como fronteira. O problema real é o ciclo (achado 1).
- O uso de `useFactory` em `DivulgacaoModule` deixa as classes de aplicação e domínio livres de decorators NestJS. É uma boa aplicação de DIP e uma raiz de composição explícita.
- `IniciativasFacadeAdapter` depender da classe concreta `IniciativasFacade` é aceitável, porque fica na camada de infraestrutura, que é onde esse acoplamento deve morar.
- `datas.ts`: funções pequenas, puras, coesas, com constante nomeada (`MS_POR_DIA`) e independentes do fuso da máquina.
- `validarIntervalo` usa a constante `MAXIMO_DIAS_INTERVALO`. A duplicação está só nos textos de documentação (achado 11).
- A repetição de `@ApiResponse` 401/403 nos dois endpoints é ruído de documentação Swagger e não afeta o projeto.
- Os DTOs Zod (`createZodDto`) e os tipos de saída (`OcorrenciaCalendario`, `AprovadaParaCalendario`) são estruturas de dados de transporte, então não os considerei Data Class problemática.
- Não há Long Parameter List: as funções recebem objetos (`dados`, `periodo`, `input`) ou no máximo três parâmetros.
