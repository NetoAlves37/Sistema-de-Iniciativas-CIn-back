# Revisão de projeto: relação entre os módulos

Base: `src/shared/domain`, as fachadas e os módulos Nest de `iniciativas`, `avaliacao`, `refinamento`, `votacao`, `divulgacao` e `identidade`, e a lista de imports entre módulos (commit b1352d3).

## Visão geral

A arquitetura segue uma convenção clara e na maior parte bem aplicada. Cada módulo publica uma fachada, e o consumidor fala com o outro módulo por uma porta própria (`application/ports/*.port.ts`), implementada por um adapter em `infrastructure/adapters`. Os problemas aparecem em três frentes. A primeira é o grafo de dependências: `iniciativas` funciona como hub e forma ciclos com três módulos. A segunda são as fachadas, que expõem tipos de domínio e operações internas. A terceira é a falta de uniformidade: cada módulo monta a fachada, nomeia tokens e adapters e acessa dados do seu próprio jeito.

## Observações de pontos positivos (não são achados)

- `shared/domain` é enxuto (`Clock`, `DomainError`, `DomainEvent`, `TransacaoPort`) e não depende de nenhum módulo, o que está correto.
- O padrão "o consumidor define a porta e implementa o adapter" (`avaliacao/application/ports/iniciativas.port`, `votacao/application/ports/iniciativa.port`, `iniciativas/application/ports/votos.port` etc.) aplica bem o DIP na maior parte das arestas. Os problemas acima são desvios desse padrão, não ausência dele.
- `TipoErroDominio` separa a semântica de negócio do status HTTP, o que é uma boa base para a padronização sugerida no achado #15.
